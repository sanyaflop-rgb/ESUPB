## ООО «Газпром переработка Благовещенск»

**Версия:** 1.0  
**Дата:** 04.10.2026  
**Статус:** база для разработки MVP в Qoder

## 0. Назначение документа

Этот документ фиксирует окончательную на текущем этапе архитектуру, модель данных и бизнес-логику приложения **PK CONTROL** — единой внутренней системы учета и анализа нарушений производственного контроля.

Документ построен на двух источниках:

1. утвержденных пользователем решениях по ТЗ;
2. фактической структуре рабочего Excel-журнала ПК III уровня за 2026 год.

Принцип: **Excel является источником реального рабочего процесса и состава данных, но не должен переноситься в приложение один-в-один.** Приложение должно хранить данные один раз и автоматически формировать своды, контроль сроков, аналитику и экспорт.

---

# 1. Основная цель системы

Заменить разрозненный Excel-процесс единым внутренним веб-приложением, доступным нескольким сотрудникам по локальной сети через обычный браузер.

Система должна централизованно хранить:

- проверки и акты/предписания;
- нарушения;
- исходные формулировки нарушения;
- нарушенные требования;
- группы и типы несоответствий;
- степень тяжести 1–9;
- проверяемые подразделения;
- объекты;
- ответственные подразделения;
- ответственных лиц;
- сроки устранения;
- статусы;
- фактические даты устранения;
- признаки устранения в ходе проверки и устранения с просрочкой;
- повторность;
- документы и фото;
- историю изменений;
- показатели эффективности производственного контроля;
- аналитические показатели и отчеты.

Главный принцип: **данные вводятся один раз и используются многократно.**

---

# 2. Виды контроля

Система едина для четырех контуров:

| Вид контроля | Учет нарушений | Контроль устранения | Аналитика |
|---|---:|---:|---:|
| ПК III уровня | Да | Да | Да |
| ПК II уровня | Да | Нет / не обязателен | Да |
| Ростехнадзор | Да | Да | Да |
| Газнадзор | Да | Да | Да |

Для ПК II интерфейс не должен визуально перегружаться полями срока, просрочки и т.п.

# 3. Архитектура приложения

## 3.1. Пользовательская модель

Около 20 сотрудников работают через браузер в локальной сети предприятия.

```text
Рабочие ПК сотрудников
        |
        | HTTP/HTTPS по LAN
        v
+-----------------------------+
|        PK CONTROL           |
|  FastAPI + Web API + UI     |
|  Один серверный процесс     |
+--------------+--------------+
               |
        +------+------+
        |             |
        v             v
    SQLite       Файловое хранилище
   локально       общая сет. папка
   на хосте       документы/фото
        |
        v
  Резервные копии
  на сетевом ресурсе
```

## 3.2. Технологическая реализация

Рекомендуемая реализация MVP:

- **Backend:** Python + FastAPI;
- **ORM:** SQLAlchemy;
- **Миграции:** Alembic;
- **Frontend:** React + TypeScript + Vite;
- **UI:** современный административный интерфейс, без зависимости от внешних облачных сервисов;
- **DB:** SQLite на хост-компьютере;
- **Файлы:** отдельная общая сетевая папка;
- **Аутентификация:** собственная, логин + пароль;
- **Сервер:** portable `PK_Server.exe`;
- **Клиент:** Edge/Chrome без установки;
- **Будущая миграция:** PostgreSQL без изменения пользовательской модели приложения.

Ключевой принцип: **SQLite не открывается пользователями напрямую. Единственная точка доступа к БД — серверный процесс.**

# 5. Доменная модель

## 5.1. Основные сущности

### `control_types`
Виды контроля:

- ПК III уровня;
- ПК II уровня;
- Ростехнадзор;
- Газнадзор.

### `inspection_kinds`
Вид мероприятия:

- Плановая;
- Внеплановая;
- Целевая.

Справочник редактируемый.

### `inspections`
Карточка проверки/акта/предписания.

Поля:

- внутренний ID;
- вид контроля;
- номер акта/предписания;
- нормализованный номер для проверки уникальности;
- дата мероприятия;
- вид мероприятия;
- статус проверки;
- комментарий;
- дата создания;
- пользователь-создатель;
- дата изменения;
- пользователь-изменивший.

### `inspection_scopes`
Области конкретной проверки.

Нужны потому, что обычно проверяется одно подразделение, но целевая проверка РПО может охватывать несколько объектов и/или подразделений.

Поля:

- inspection_id;
- department_id;
- object_id;
- при необходимости комментарий.

Одна проверка может иметь много областей.

### `violations`
Главная сущность учета нарушения.

Поля:

- ID;
- inspection_id;
- inspection_scope_id;
- формулировка нарушения;
- нарушенное требование;
- violation_type_id;
- текущая степень тяжести;
- due_date;
- original_due_date;
- due_date_basis;
- due_date_source_text;
- document_received_date;
- current_status;
- elimination_date;
- eliminated_during_inspection;
- eliminated_late;
- days_overdue_current;
- days_overdue_at_elimination;
- repeat_status;
- source_import_id;
- annulled;
- annulled_at;
- annulled_by;
- annulment_reason;
- created_at;
- created_by;
- updated_at;
- updated_by.

### `violation_groups`
Верхний уровень классификации.

Например:

1. Документация  
2. Экспертиза промышленной безопасности  
3. Готовность к ликвидации последствий аварий и инцидентов  
4. Оформление информационными знаками и знаками безопасности  
5. Содержание объектов и оборудования  
6. Организация рабочего процесса и безопасности персонала

### `violation_types`
45 детализированных типов несоответствий.

Поля:

- внутренний ID;
- код (`1.1`, `1.2`, `5.10` и т.п.);
- наименование;
- группа;
- текущая степень тяжести;
- признак активности;
- порядок отображения;
- дата создания/изменения.

Код является стабильным идентификатором для бизнес-аналитики.

### `persons`
Справочник ответственных лиц, независимо от наличия учетной записи в приложении.

Поля:

- ФИО/отображаемое имя;
- должность;
- подразделение;
- признак активности.

Это позволяет назначать ответственным сотрудника, у которого нет учетной записи в системе.

### `departments`
Справочник структурных подразделений.

Поля:

- код;
- название;
- родительское подразделение при необходимости;
- активность;
- порядок отображения.

### `objects`
Справочник установок, цехов, объектов и производственных площадок.

Поля:

- код/обозначение;
- название;
- подразделение-владелец;
- активность;
- порядок отображения.

Подразделение и объект — разные сущности.

### `violation_responsible_departments`
Связь нарушения с одним или несколькими ответственными подразделениями.

### `violation_responsible_persons`
Связь нарушения с одним или несколькими ответственными лицами.

### `attachments`
Файлы, связанные с проверкой или нарушением.

### `deadline_changes`
История переноса/изменения сроков.

### `repeat_links`
Связи между потенциально повторными нарушениями.

### `audit_log`
Полный журнал изменений.

### `users`
Учетные записи пользователей.

### `roles`
Роли доступа.

### `effectiveness_assessments`
Оценка эффективности производственного контроля за период и объект оценки.

### `effectiveness_inputs`
Исходные показатели, которые вводит специалист для ручных/смешанных критериев.

### `effectiveness_results`
Рассчитанные значения критериев: факт, порог, балл, Н/П, пояснение.

# 6. Правило для многоподраздельных проверок

Обычная проверка обычно относится к одному подразделению.

Целевая проверка РПО может охватывать:

- несколько объектов;
- несколько подразделений;
- разные сочетания объект + подразделение.

Поэтому проверка не должна иметь только одно поле подразделения.

Для этого используется сущность `inspection_scopes`.

Каждое нарушение привязывается к конкретной области проверки.

Пример:

```text
Проверка: Целевая проверка РПО №46ц-26
|
+-- Производство №4 / МЦКиФХ
+-- Производство №4 / АСН
+-- Производство №2 / УПЭиШФЛУ №1
+-- ЦКГ / ДКС метановой фракции №4
```

---

# 7. Нумерация актов/предписаний

Номер задается пользователем вручную.

Автоматическая нумерация на MVP не реализуется.

Уникальность:

```text
Вид контроля + нормализованный номер документа
```

Это означает, что один и тот же номер может существовать в разных контурах контроля.

Например:

- ПК III / №15-26;
- ПК II / №15-26.

---

# 8. Состояния проверки

Используются три состояния:

- **Черновик**;
- **Редактируется**;
- **В работе**.

Состояние проверки не должно блокировать нормальную работу с нарушениями.

Нет отдельного обязательного статуса «Завершена».

---

# 9. Карточка нарушения

## 9.1. Обязательные поля

- формулировка нарушения;
- нарушенное требование;
- тип несоответствия;
- ответственное подразделение;
- объект/область проверки;
- вид контроля через связь с проверкой.

## 9.2. Поля срока

Для ПК III, Ростехнадзора и Газнадзора:

- дата получения документа;
- исходный срок;
- текущий срок;
- основание срока;
- текст срока из первичного документа.

Если срок задается количеством дней от даты получения документа, система может рассчитать конечную дату.

Если в исходном документе уже есть конечная дата, она импортируется напрямую.

## 9.3. Ответственные

У одного нарушения:

- может быть несколько ответственных подразделений;
- может быть несколько ответственных лиц.

---

# 10. Статусы нарушения

Используются только три текущих статуса:

1. **Устранено**
2. **Не устранено**
3. **Просрочено**

Логика:

```text
Есть дата устранения
    -> Устранено

Нет даты устранения + срок не истек
    -> Не устранено

Нет даты устранения + срок истек
    -> Просрочено
```

Для ПК II поля и логика контроля сроков не являются обязательными и не должны перегружать интерфейс.

---

# 11. Просрочка после устранения

Текущий статус после устранения всегда:

> **Устранено**

Но дополнительно система хранит автоматически вычисляемый признак:

> **Устранено с просрочкой = Да/Нет**

Пример:

```text
Срок:                  01.06.2026
Дата устранения:       13.06.2026
Текущий статус:        Устранено
Устранено с просрочкой: Да
Дней просрочки:        12
```

Это позволяет корректно считать:

- устранено всего;
- устранено в срок;
- устранено с просрочкой;
- текущие просроченные.

---

# 12. Устранение в ходе проверки

Флаг:

> `eliminated_during_inspection = true/false`

При установке признака система предлагает дату проверки как дату устранения, но пользователь должен иметь возможность проверить значение.

---

# 13. Перенос срока

Право изменения срока имеют только:

- Специалист СППБиБДД;
- Администратор.

Отдельного согласующего не требуется.

При изменении срока обязательно фиксируются:

- старый срок;
- новый срок;
- причина;
- кто изменил;
- дата/время изменения.

Историю нельзя удалять.

---

# 14. Аннулирование

Физическое удаление нарушений запрещено.

Вместо него используется:

> **Аннулировать запись**

Право:

- Специалист СППБиБДД;
- Администратор.

Обязательна причина аннулирования.

Аннулированная запись исключается из обычной аналитики, но остается в аудите.

---

# 15. Классификация нарушений

Используется трехуровневая модель:

```text
Группа
   -> Тип несоответствия
      -> Степень тяжести
```

В интерфейсе пользователь выбирает конкретный тип несоответствия.

После выбора система автоматически показывает степень тяжести, которая в текущем справочнике привязана к типу.

Пример:

```text
Группа: 5. Содержание объектов и оборудования
Тип: 5.10. Несоответствия при проведении работ повышенной опасности
Степень тяжести: 9
```

Автоматического текстового ИИ-классификатора на MVP нет.

---

# 16. Изменение справочника категорий/типов

Справочник является живым и редактируемым.

Администратор может:

- добавить тип;
- изменить название;
- изменить степень тяжести;
- деактивировать тип;
- изменить порядок отображения.

Новые нарушения используют актуальное состояние справочника.

Для существующих нарушений применяется правило пользователя:

> если справочник изменен, текущая категория и текущая степень тяжести нарушения должны отражать актуальное состояние справочника.

При этом история должна сохранять прежнее состояние:

```text
Было: степень 7
Стало: степень 8
Кто: Администратор
Когда: 15.11.2026
Причина: изменение справочника
```

Удаление категорий физически не допускается — используется деактивация.

# 17. История изменений

Аудит обязателен.

Каждое существенное изменение фиксируется:

- дата/время;
- пользователь;
- сущность;
- запись;
- действие;
- старое значение;
- новое значение;
- причина, если обязательна.

Особенно важно фиксировать:

- создание нарушения;
- изменение формулировки;
- изменение требования;
- изменение категории;
- изменение степени тяжести;
- изменение ответственных;
- изменение срока;
- перенос срока;
- добавление/удаление вложения;
- изменение статуса;
- дату устранения;
- аннулирование;
- подтверждение повторности.

---

# 18. Повторные нарушения

На MVP применяется мягкий механизм.

Система ищет потенциальные совпадения по комбинации:

- объект;
- проверяемое подразделение;
- категория/тип;
- ответственное подразделение;
- ответственное лицо;
- похожесть формулировок.

Система не принимает решение автоматически.

Она показывает:

> **«Возможно повторное нарушение»**

Пользователь выбирает:

- Подтвердить повтор;
- Не повтор;
- Отложить.

Повторные нарушения можно связывать цепочкой:

```text
Первичное
   -> Повторное №1
      -> Повторное №2
```

- аналитика;
- экспорт;
- оценка эффективности ПК.

- просмотр всех данных;
- аналитика;
- отчеты;
- экспорт;
- ограниченное редактирование только если это отдельно разрешено ролью.

## Ответственный подразделения

- просмотр назначенных ему нарушений;
- добавление подтверждений;
- загрузка фото/документов;
- указание фактической даты устранения;
- комментарии;
- запрос на перенос срока через интерфейс без отдельного согласующего.

Ответственный подразделения не изменяет исходную формулировку нарушения, нарушенное требование, тип несоответствия или степень тяжести.

# 22. Дашборд

Главный экран должен быть выполнен на основе предоставленного пользователем UI-референса. Это именно дизайн-референс: предметная логика, состав данных и существующие функции настоящего документа не изменяются.

## Компоновка главного экрана

Рабочая область дашборда располагается справа от sidebar и строится вертикально:

1. заголовок страницы и выбор периода;
2. ряд из 6 KPI-карточек;
3. ряд из 4 основных аналитических виджетов;
4. большой рабочий реестр нарушений;
5. ряд быстрых действий.

Экран должен выглядеть как единое рабочее пространство, а не как набор разрозненных страниц.

## Верхняя часть

В соответствии с референсом:

- основной заголовок «Дашборд»;
- справа — дата/время и выбор текущего периода;
- над рабочей областью сохраняется глобальный поиск из header.

## KPI

Сохраняются 6 ранее определенных показателей:

- Проверок;
- Нарушений;
- Устранено;
- Не устранено;
- Просрочено;
- Срок ≤ 7 дней.

Каждая KPI-карточка в визуальном стиле референса содержит:

- небольшую пиктограмму;
- название показателя;
- крупное числовое значение;
- при наличии — изменение относительно предыдущего периода;
- краткую подпись/контекст показателя.

Карточки должны различаться по смыслу за счет умеренных цветовых акцентов, а не за счет насыщенной заливки всего блока.

## Основные аналитические виджеты

Первый экран визуально показывает четыре основных блока:

### 1. Динамика выявления нарушений

Комбинированный/столбчатый график в стиле референса с разбивкой по видам контроля и временной шкалой.

### 2. Распределение по рангам

Кольцевая диаграмма по степеням тяжести 1–9 с легендой справа и общим количеством нарушений в центре.

### 3. По подразделениям

Горизонтальные полосы с количеством нарушений и долей от общего количества.

### 4. По видам контроля

Кольцевая диаграмма с распределением нарушений по четырем видам контроля.

Остальные согласованные показатели аналитики (категории/типы, повторные нарушения и др.) должны быть доступны в разделе **Аналитика** и не исчезают из системы. Они просто не перегружают первый экран.

## Рабочий реестр

Под аналитическими блоками расположен основной широкий табличный блок. Визуально он должен занимать значительную часть дашборда и быть главным рабочим элементом экрана.

Над таблицей размещаются вкладки/быстрые представления, например:

- Последние нарушения;
- Просроченные;
- Ближайшие сроки;
- и другие согласованные представления без изменения бизнес-логики.

Справа над таблицей размещаются компактные действия:

- экспорт;
- фильтры;
- настройка отображения колонок.

Сама таблица должна быть плотной, но читаемой: тонкие границы, небольшие отступы, небольшие статусные чипы, закрепленная строка заголовков при прокрутке внутри таблицы.

## Быстрые действия

В нижней части дашборда расположить крупные компактные action-карточки, аналогичные референсу:

- Новая проверка;
- Импорт из Word/Excel;
- Аналитика;
- Отчеты и экспорт;
- Справочники.

## Интерактивность

Любой фильтр должен пересчитывать KPI и графики на том же наборе данных.

Пример:

```text
ПК III
+ Производство №4
+ степень 7–9
+ не устранено
+ просрочено
```

После применения фильтров весь дашборд сохраняет ту же визуальную компоновку, меняя только данные и результаты агрегатов.

## Принцип визуального поведения

- минимум декоративных элементов;
- приоритет данных над графической декоративностью;
- одинаковая визуальная система карточек, таблиц, фильтров и графиков;
- скругления умеренные;
- светлый основной фон;
- темно-синий sidebar;
- синие акцентные элементы;
- цвет используется осмысленно для KPI, рангов и статусов;
- интерфейс должен быть визуально близок к предоставленному референсу по плотности, иерархии и компоновке.

# 25. Подразделенческая аналитика

Если нарушение связано с несколькими ответственными подразделениями, в разрезе ответственных подразделений одна запись может учитываться для каждого выбранного подразделения.

При этом общий показатель «количество нарушений» считается по уникальным нарушениям и не дублируется.

Интерфейс должен явно показывать, когда используется многозначная ответственность, чтобы суммы по подразделениям не воспринимались как арифметическая сумма общего количества.

# 26. Оценка эффективности производственного контроля

В приложении должен быть отдельный модуль:

> **Производственный контроль → Оценка эффективности**

Оценка строится по **24 критериям**.

Общий результат:

> среднее арифметическое применимых баллов.

Критерии с `Н/П` в среднее не включаются.

Границы итоговой оценки:

- **< 1,00 — неудовлетворительно**;
- **≥ 1,00 — удовлетворительно**.

Это устраняет пересечение исходной формулировки на значении 1,00.

# 27. Источник данных для оценки эффективности

Принцип:

> **пользователь вводит исходные данные, система сама рассчитывает проценты, коэффициенты и баллы.**

Пользователь не должен вручную выбирать 0/1/2 там, где показатель можно вычислить автоматически.

Для показателей, которые не применяются к конкретному подразделению/периоду, используется:

> **Н/П**

и критерий исключается из среднего.

# 28. 24 критерия оценки эффективности

## 1. Организация производственного контроля

### 1.1. ПК II уровня

**1.1.1. Своевременность и полнота предоставления сведений об осуществлении АПК на II уровне**

- 0: сведения не представлены или представлены позднее 5 рабочих дней установленного срока;
- 1: представлены с нарушением сроков, но не более чем на 5 рабочих дней;
- 2: представлены не позднее 10 рабочих дней месяца, следующего за отчетным кварталом;
- период: ежеквартально.

**1.1.2. Выполнение установленной периодичности проведения проверок АПК на II уровне объектов структурного подразделения**

- 0: нарушение периодичности более чем на 5 календарных дней;
- 1: нарушение периодичности, но не более чем на 5 календарных дней;
- 2: проверки не реже одного раза в 10 календарных дней;
- период: ежеквартально.

**1.1.3. Наличие АОП 3-го уровня опасности**

- 0: наличие АОП 3-го уровня по вине работника или эксплуатирующей организации;
- 1: не используется;
- 2: отсутствие АОП 3-го уровня по вине работника или эксплуатирующей организации;
- период: ежеквартально.

**1.1.4. Разработка годового графика противоаварийных тренировок структурного подразделения**

- 0: не разработан или позднее 5 рабочих дней установленного срока;
- 1: нарушение срока, но не более чем на 5 рабочих дней;
- 2: разработан не позднее 30 ноября предыдущего года;
- период: календарный год.

**1.1.5. Разработка графиков технического освидетельствования, диагностирования, испытаний, поверки и связанных планов**

- 0: не разработаны или позднее 5 рабочих дней установленного срока;
- 1: нарушение срока, но не более чем на 5 рабочих дней;
- 2: разработаны не позднее 28 декабря предыдущего года;
- период: календарный год.

### 1.2. ПК III уровня

**1.2.1. Разработка планов мероприятий в области промышленной безопасности, включая работы по осуществлению производственного контроля и годовые графики плановых проверок ПК III уровня**

- 0: не разработаны или позднее 5 рабочих дней установленного срока;
- 1: нарушение срока, но не более чем на 5 рабочих дней;
- 2: разработаны не позднее 28 декабря предыдущего года;
- период: календарный год.

**1.2.2. Разработка графика противоаварийных тренировок Общества**

- 0: не разработан или позднее 5 рабочих дней установленного срока;
- 1: нарушение срока, но не более чем на 5 рабочих дней;
- 2: разработан не позднее 15 декабря предыдущего года;
- период: календарный год.

**1.2.3. Наличие АОП 1-го, 2-го уровня опасности, несчастных случаев на ОПО**

- 0: наличие АОП 1-го/2-го уровня по вине работника или эксплуатирующей организации;
- 1: не используется;
- 2: отсутствие АОП 1-го/2-го уровня по вине работника или эксплуатирующей организации;
- период: ежеквартально.

**1.2.4. Выполнение графика плановых проверок производственного контроля III уровня**

- 0: нарушение сроков более чем на 5 календарных дней;
- 1: нарушение сроков, но не более чем на 5 календарных дней;
- 2: в установленные сроки;
- период: ежеквартально.

При этом система не должна позволять вводить сам балл вместо исходных данных.

# 30. Отчеты и экспорт

Отдельного конструктора презентаций нет.

Поддерживаются:

- Excel;
- PDF;
- PNG;
- SVG.

Минимальный набор готовых отчетов:

1. Реестр нарушений;
2. Просроченные нарушения;
3. Анализ за период;
4. Оценка эффективности ПК;
5. Повторные нарушения;
6. Анализ по подразделениям.

Экспорт всегда учитывает:

- выбранный период;
- выбранный вид контроля;
- активные фильтры.

Перед экспортом пользователь видит краткое описание того, какой набор данных попадет в файл.

# 31. Резервное копирование

SQLite хранится локально на хосте.

Резервные копии:

- ежедневно;
- на общую сетевую папку;
- с периодическими более длительными контрольными копиями.

Резервирование должно выполняться безопасным способом, совместимым с работающей SQLite БД, а не простым неконтролируемым копированием файла во время записи.

Должна быть функция проверки наличия последней успешной копии.

# 37. Критерии готовности MVP

MVP считается готовым, если:

- пользователь может войти по роли;
- можно создать любую из 4 проверок;
- проверка может иметь несколько областей объект+подразделение;
- можно создать нарушение вручную;
- можно импортировать Word/Excel;
- есть preview импорта;
- ошибки видны до сохранения;
- доступны 45 типов;
- степень тяжести подставляется автоматически;
- изменение справочника отражается в текущих нарушениях и записывается в историю;
- для ПК III/Ростехнадзора/Газнадзора работает контроль сроков;
- ПК II не перегружен сроками;
- поддерживаются три статуса;
- учитывается устранение с просрочкой;
- учитывается устранение в ходе проверки;
- работает перенос срока специалистом/администратором;
- работает мягкое определение повторности;
- работают комбинированные фильтры;
- дашборд пересчитывается по фильтрам;
- есть периодический анализ;
- есть оценка по 24 критериям;
- Н/П исключается из среднего;
- есть экспорт Excel/PDF/PNG/SVG;
- есть аудит;
- есть резервные копии;
- приложение работает как сервер на хосте и доступно через браузер по LAN.

---

# 38. Что сознательно отложено

Не включать в MVP:

- внешние уведомления;
- электронную почту/ЭП;
- AD/LDAP;
- интеллектуальное ИИ-сопоставление повторных нарушений;
- автоматическую нумерацию актов;
- миграцию исторических Excel-данных — будет отдельным этапом после предоставления рабочего массива;
- отдельный конструктор презентаций.

---

# 39. Ключевой принцип разработки

**Не делать приложение как «новый Excel в браузере».**

Правильная модель:

```text
Проверка
    ↓
Нарушения
    ↓
Структурированные справочные данные
    ↓
Автоматические расчеты
    ↓
Контроль сроков
    ↓
Аналитика
    ↓
Отчеты / экспорт
```

Excel становится способом импорта и экспорта, а не центральной базой.
