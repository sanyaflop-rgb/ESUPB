# 3. Главный принцип разработки

Не создавай «Excel в браузере».

Создавай нормальную информационную систему:

```text

   ↓

   ↓

   ↓

   ↓
```

Одни и те же данные не должны дублироваться в разных таблицах/листах.

---

# 4. Ключевое техническое решение

MVP должен работать следующим образом:

```text
20 рабочих ПК
      ↓
обычный браузер Edge/Chrome
      ↓
локальная сеть предприятия
      ↓
PK_Server.exe на одном хосте
      ↓
FastAPI
      ↓
SQLite локально на хосте
      ↓
общая сетевая папка для документов и backup
```

**Никогда не размещай сам SQLite-файл на общей SMB-папке для прямого доступа нескольких клиентов.**

Только серверный процесс работает с БД.

# 11. Проверки

Четыре вида контроля:

- ПК III уровня;
- ПК II уровня;
- Ростехнадзор;
- Газнадзор.

Виды мероприятия:

- Плановая;
- Внеплановая;
- Целевая.

Номер акта вводится вручную.

Уникальность номера:

```text
control_type + normalized_document_number
```

Автоматической нумерации пока нет.

Состояния проверки:

- Черновик;
- Редактируется;
- В работе.

Отдельного обязательного «Завершено» нет.

---

# 12. Области проверки

Одна проверка обычно относится к одному подразделению, но может содержать несколько объектов.

Целевая проверка РПО может охватывать несколько подразделений и объектов.

Поэтому используй:

```text
inspection
    ↓
inspection_scope
    ↓
department + object
```

Каждое нарушение привязано к конкретной области проверки.

# 15. Изменение справочника и историчность

Критически важно:

- не удалять тип физически;
- использовать активность;
- хранить код;
- вести историю изменений.

Если администратор изменяет степень тяжести типа:

```text
Тип 5.10
Было: 9
Стало: 8
```

то текущие связанные нарушения должны отражать актуальное состояние справочника.

При этом в `audit_log` должно сохраниться прежнее значение.

Не теряй исторические изменения.

# 16. Статусы нарушений

Только:

- Устранено;
- Не устранено;
- Просрочено.

Алгоритм:

```text
if elimination_date exists:
    status = Устранено
elif due_date is null:
    status = Не устранено   # для контуров, где срок применяется только при наличии срока
elif today <= due_date:
    status = Не устранено
else:
    status = Просрочено
```

Для ПК II сроковой блок не обязателен и может отсутствовать.

---

# 17. Устранение с просрочкой

Не создавай статус «Просрочено — устранено».

Храни:

```text
status = Устранено
eliminated_late = true
```

Рассчитывай:

- days_overdue_at_elimination;
- was_overdue.

---

# 18. Устранено в ходе проверки

Храни отдельный Boolean:

```text
eliminated_during_inspection
```

При этом current status = `Устранено`.

# 20. Аннулирование вместо удаления

Физическое удаление нарушения запрети.

Используй soft-delete / annulment:

```text
annulled = true
annulment_reason = required
annulled_by
annulled_at
```

Обычная аналитика исключает аннулированные записи.

Аудит сохраняет их.

# 26. Дашборд

Создай интерфейс на основе предоставленного пользователем UI-референса. Референс определяет только визуальную подачу и компоновку. Не изменяй ради дизайна утвержденную бизнес-логику, модель данных, права, статусы, расчеты или состав функций.

## Общая композиция

Главный экран должен иметь следующую визуальную иерархию:

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Верхний header: поиск · уведомления · пользователь                  │
├──────────────┬───────────────────────────────────────────────────────┤
│ Темно-синий  │ Заголовок страницы + период                         │
│ sidebar      ├───────────────────────────────────────────────────────┤
│              │ 6 KPI-карточек                                       │
│              ├───────────────────────────────────────────────────────┤
│              │ 4 аналитических виджета                              │
│              ├───────────────────────────────────────────────────────┤
│              │ Рабочий реестр нарушений                             │
│              ├───────────────────────────────────────────────────────┤
│              │ Быстрые действия                                     │
└──────────────┴───────────────────────────────────────────────────────┘
```

Не делать дашборд набором отдельных полноэкранных карточек или набором вкладок, между которыми пользователь постоянно переключается.

## Верхний header

Сохрани визуальную логику референса:

- слева — фирменный знак/щит, название «Производственный контроль» и подпись «Единая система учета и анализа нарушений»;
- по центру — длинное поле глобального поиска;
- справа — уведомления с индикатором, пользователь, ФИО и роль;
- header темно-синий, компактный, с четким разделением на зоны;
- визуально header должен быть значительно ниже по высоте, чем рабочая область.

## Левая панель

Темно-синий вертикальный sidebar по всему рабочему экрану.

- иконка перед каждым пунктом;
- короткие понятные названия;
- активный раздел — яркая синяя плашка с мягкими скруглениями;
- вложенные пункты показываются непосредственно под родительским разделом;
- внизу — статус системы, версия и служебная информация;
- sidebar не должен выглядеть как тяжелое многоуровневое дерево настроек.

## Основные KPI

Сохрани все 6 согласованных KPI:

- Проверок;
- Нарушений;
- Устранено;
- Не устранено;
- Просрочено;
- Срок ≤ 7 дней.

Каждая карточка должна иметь структуру: иконка → название → крупное число → изменение/контекст. Используй разные умеренные акцентные цвета для смыслового различения карточек.

## Аналитические виджеты первого экрана

В соответствии с референсом на дашборде одновременно показывай четыре основных блока:

1. **Динамика выявления нарушений** — столбчатый график с временной шкалой и легендой по видам контроля.
2. **Распределение по рангам** — кольцевая диаграмма по степеням тяжести 1–9 с легендой и общим количеством в центре.
3. **По подразделениям** — горизонтальные полосы с абсолютным значением и долей.
4. **По видам контроля** — кольцевая диаграмма по ПК III, ПК II, Ростехнадзору и Газнадзору.

Остальные аналитические срезы, уже предусмотренные настоящим промптом, не удалять. Размещение на первом экране не является обязательным: они доступны через раздел **Аналитика**.

## Рабочая таблица

Под графиками должен располагаться широкий реестр последних нарушений.

Верхняя строка блока:

- вкладки представлений;
- кнопка экспорта;
- кнопка фильтров;
- настройка отображения колонок.

Таблица должна быть главным рабочим элементом дашборда: компактная, с небольшими отступами, четкой сеткой, читаемыми заголовками колонок и статусными чипами.

## Быстрые действия

В нижней части экрана — горизонтальный ряд action-карточек:

- Новая проверка;
- Импорт из Word/Excel;
- Аналитика;
- Отчеты и экспорт;
- Справочники.

## Визуальная плотность

Используй светлый рабочий фон, белые карточки, тонкие границы, умеренные скругления и сдержанные тени/без тяжелых теней. Основной визуальный акцент — данные и активные состояния, а не декоративные эффекты.

## Адаптивность

На узких экранах композиция должна перестраиваться без потери данных: sidebar сворачивается/переходит в компактный режим, KPI переносятся, аналитические блоки становятся вертикальными, таблица получает локальную горизонтальную прокрутку.

# 29. Оценка эффективности: 24 критерия

# 32. Критерий 2.1.7

Особая логика.

Ввод:

```text
Количество выданных нарядов-допусков на РПО
```

Система самостоятельно считает количество нарушений ПК II, связанных с безопасным проведением РПО, используя типы:

- `1.1`;
- `5.10`.

Формула:

```text
RPO_violations / permits
```

Порог:

```text
< 0.1  → 0
= 0.1  → 1
> 0.1  → 2
```

# 33. Н/П

Н/П — это полноценное состояние результата критерия.

Пример:

```text
2.1.5
Мероприятий технического расследования за период нет
→ Н/П
```

Критерий исключается из среднего.

Нельзя автоматически превращать отсутствие мероприятий в 100% выполнения.

Это критически важно.

# 35. Документы

Храни физические файлы не внутри SQLite, а в файловой системе.

SQLite хранит metadata/path.

Файлы группируй по:

```text
год / вид контроля / номер документа
```

При сохранении:

- проверяй имя;
- создавай директории;
- сохраняй metadata;
- рассчитывай hash;
- логируй действие.

# 38. Безопасность

Минимум:

- Argon2id или эквивалентный современный password hash;
- HttpOnly secure cookie/session;
- CSRF-защита для cookie-based mutating requests;
- серверная RBAC-проверка;
- валидация входных данных;
- безопасная обработка путей файлов;
- лимиты на загрузку файлов;
- блокировка directory traversal;
- исключение секретов из Git;
- централизованное логирование ошибок без раскрытия секретов.

Приложение рассчитано на внутреннюю LAN, но не должно считать внутреннюю сеть абсолютной границей безопасности.

# 39. UI/UX требования

Весь интерфейс должен использовать предоставленный пользователем референс как основной визуальный ориентир. Это изменение относится только к дизайну и UX-подаче; существующие функциональные и бизнес-требования настоящего промпта сохраняются без изменений.

## Основная стилистика

- современный деловой технологичный интерфейс;
- темно-синий верхний header и левый sidebar;
- очень светлый серо-голубой рабочий фон;
- белые рабочие карточки с тонкой границей;
- умеренные скругления;
- основной акцент — синий;
- дополнительные акценты для KPI и статусов — зеленый, желтый, красный, фиолетовый;
- четкая типографическая иерархия;
- компактная, но не перегруженная плотность информации.

## Компоновка

Ориентироваться на структуру референса:

**header → sidebar → заголовок/период → 6 KPI → 4 аналитических блока → широкий реестр → быстрые действия.**

## Компоненты

- KPI-карточки — одинаковая геометрия и высота;
- графики — аккуратные, без лишней декоративности;
- диаграммы — с читаемой легендой и общим итогом в центре там, где используется кольцевая схема;
- таблицы — основное рабочее пространство, с четкими колонками и компактными статусными чипами;
- фильтры — компактные и располагаются рядом с рабочим контентом;
- иконки — простые линейные/контурные пиктограммы в единой стилистике;
- action-карточки — крупные точки быстрого входа в основные операции.

## Цветовая логика

Не использовать яркие цвета для декоративной заливки больших областей. Цвет должен сообщать смысл:

- синий — основной акцент и активные элементы;
- зеленый — положительный результат/устранение;
- желтый/оранжевый — внимание и приближающийся срок;
- красный — просрочка/критическое состояние;
- фиолетовый — отдельный информационный KPI/срез.

## Поведение

Главная страница должна оставаться визуально стабильной при фильтрации: меняются цифры, графики и строки реестра, но не сама структура экрана.

Не делать визуально «типичный старый корпоративный Excel». Не превращать интерфейс в декоративный landing page.

# 50. Главная цель

Получить надежное внутреннее приложение PK CONTROL, которое:

- реально заменяет текущий Excel-процесс;
- сохраняет исходные формулировки нарушений;
- структурирует данные;
- автоматически считает сроки, статусы и аналитику;
- поддерживает 4 вида контроля;
- поддерживает 45 детализированных типов несоответствий;
- поддерживает степень тяжести 1–9;
- ведет аудит;
- позволяет работать нескольким сотрудникам одновременно через браузер;
- не требует установки клиента;
- может быть запущено с одного portable `.exe`;
- подготовлено к будущему PostgreSQL;
- не зависит от Интернета;
- легко расширяется новыми справочниками, критериями и отчетами.

**Приоритеты:** корректность бизнес-логики > сохранность данных > безопасность > тестируемость > удобство работы > визуальная красота.
