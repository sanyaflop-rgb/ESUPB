# Модель данных

Этап 2 вводит первую миграцию `20261005_01`: пользователи, роли, назначения ролей, аудит и следующие справочники: подразделения, объекты, лица, виды контроля, виды проверок, группы и типы нарушений.

Во всех таблицах используются UUID-идентификаторы и время создания/изменения. Справочники имеют `is_active` и `display_order`; физическое удаление API не предоставляет. Внешние ключи используют `RESTRICT`, чтобы будущие исторические записи не теряли связи.

Начальные данные миграции: 4 роли, 4 вида контроля (у ПК II `has_deadline_control = false`), 3 вида проверок, 6 групп и 45 типов несоответствий с исходными степенями тяжести.

Этапы 3–5 добавили через миграции `43594a0dc7a3`, `20261006_01`, `20261006_02` и `20261008_01`: проверки и области проверки, нарушения с индивидуальными мерами устранения, историю переносов сроков, связи повторности, а также оценку эффективности производственного контроля.

Миграция `20261008_01` вводит три таблицы оценки эффективности:

- `assessment_criteria` — справочник из 24 критериев оценки (`criterion_code`, `section_code/title`, `name`, `subject_type` подразделение/Служба, `period_type` критерия, `input_type` ручной/авто/смешанный, `formula_type`, `thresholds`, `score_mapping`, `applicability_rule`, `input_fields` — все JSON). Уникальность `criterion_code + version`, поле `active_from` готово к версионированию методики.
- `assessment_facts` — исходные данные, введённые пользователем: значения полей критерия (`values` JSON), признак `not_applicable`, комментарий. Уникальность по области действия: критерий + период (год/тип/подпериод) + `subject_key` (`department:{uuid}` или `service`). Факты хранятся на период оценки, а не на период критерия.
- `assessment_results` — зафиксированные результаты: средний балл, вердикт, счётчики (учитывается/Н/П/нет данных) и `criteria_payload` — полный срез критериев с баллами и причинами на момент фиксации. Уникальность по периоду + объекту; повторная фиксация обновляет запись (upsert).

Служба ППБиБДД как объект оценки не имеет отдельной записи в `departments` и адресуется константным `subject_key = 'service'`.

Ключевая будущая связь: `проверка → области проверки → нарушения`. Целевая проверка может включать несколько сочетаний «подразделение + объект». Номер документа хранится отдельно вместе с нормализованным ключом, уникальным в паре с видом контроля.
