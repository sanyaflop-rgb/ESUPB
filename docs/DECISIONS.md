# Принятые решения

Дата фиксации: 2026-10-05 (дополнено 2026-10-07 и 2026-10-08).

| ID | Решение | Обоснование |
| --- | --- | --- |
| D-001 | PK CONTROL разрабатывается в репозитории ESUPB. | Решение пользователя. |
| D-002 | Случай нулевого числа нарядов-допусков в критерии 2.1.7 даёт Н/П. Н/П исключается из среднего балла. | Архитектурный документ содержит специальное правило; оно дополняет общий принцип Н/П. |
| D-003 | Макет от 04.10.2026 используется только как визуальный референс. | Бизнес-правила, статусы и состав разделов определяет архитектура проекта. |
| D-004 | Разделитель в номере документа — `/`. Нормализация удаляет `№`, игнорирует регистр и лишние пробелы, приводит `-`, `–`, `_` к `/`. | Требуется единый ключ для ручной нумерации: например, `42ц/26` и `42ц-26` — один документ. |
| D-005 | Сроки считаются в календарных днях. | Решение пользователя. |
| D-006 | Статусы нарушений ПК III и внешнего контроля: только «Устранено», «Не устранено», «Просрочено». | «На контроле» не является статусом и не переносится из визуального макета. |
| D-007 | У ПК II нет контроля сроков: нет срока устранения, просрочки и попадания в представления «Просроченные»/«Ближайшие сроки». | Прямое требование пользователя и архитектуры. |
| D-008 | Ответственное подразделение подаёт заявку на перенос срока (комментарий и желаемая дата); перенос выполняет только Специалист или Администратор и логируется. | Сохраняет разграничение полномочий и прослеживаемость. |
| D-009 | При импорте многообластной проверки строки автоматически распределяются по подразделению и объекту, если соответствующие колонки найдены; иначе область выбирает пользователь. | Снижает ручную работу, не теряя контроля над неоднозначными файлами. |
| D-010 | Переносим существующий журнал ПК III уровня за 2026 год. Сводные листы используем для сверки, а справочники собираем из журнала и реестров. | Решение пользователя. |
| D-011 | Справочники деактивируются, а нарушения аннулируются с причиной — физическое удаление не применяется. | Сохранность и аудит данных. |
| D-012 | SQLite работает исключительно локально на сервере. Документы и резервные копии размещаются в сетевых папках; SQL и модель должны оставаться совместимыми с PostgreSQL. | Защита базы от проблем SMB и готовность к масштабированию. |
| D-013 | Поля «основание срока» и «источник срока» исключены. | Решение пользователя: поля срока не участвуют в расчётах. Отступление от п. 9.2 архитектурного документа. |
| D-014 | Нарушение — общий факт; его устранение ведётся отдельными мерами: подразделение, объект, сотрудник, мероприятие, свой срок, статус, дата устранения и история переносов. «Области проверки» не применяются. | Одно нарушение может требовать разных действий от нескольких ответственных. Общий статус «Устранено» присваивается только после выполнения всех мер; в общем KPI факт нарушения считается один раз, контроль исполнения — по мерам. |
| D-015 | Доработки импорта (интерактивное сопоставление колонок, выбор таблицы Word и строки начала данных, расширенные тесты) отложены на поздний этап проектирования. Базовая цепочка импорта работает: предпросмотр, валидация, подтверждение с записью в базу и журналирование. | Решение пользователя от 2026-10-07: продолжить разработку со следующего раздела архитектуры. |
| D-016 | Заявки на перенос срока (deadline_change_requests) отложены: перенос выполняет Специалист или Администратор напрямую, изменение сохраняется в истории сроков. Таблица заявок сохранена в схеме для будущего этапа. | Мастер-промпт не описывает процесс согласования заявок; прямой перенос с журналированием достаточен для текущего этапа (см. D-008). |
| D-017 | Оценка эффективности ПК выполняется за квартал, полугодие, 9 месяцев и год. Период «9 месяцев» добавлен сверх архитектурного документа. | Решение пользователя от 2026-10-08. |
| D-018 | Объект оценки: критерии ПК II уровня оцениваются по подразделению; критерии ПК III уровня и внешних органов — по единому фиксированному объекту «Служба промышленной, пожарной безопасности и безопасности дорожного движения». Критерии другого объекта дают «Н/П». | Решение пользователя от 2026-10-08. |
| D-019 | В критериях «устранено в срок» (2.1.4, 2.2.1) знаменатель — только меры с наступившими сроками; меры с будущими сроками не учитываются. | Решение пользователя от 2026-10-08: незавершённые сроки не должны занижать оценку. |
| D-020 | Критерий 1.1.2 (периодичность проверок АПК II уровня) — ручной ввод «да/нет»: пользователь сам определяет, соблюдается ли периодичность. | Решение пользователя от 2026-10-08. |
| D-021 | Критерии 1.1.1 (своевременность подачи сведений) и 2.2.8 (целевые проверки РПО) заполняются ручным вводом исходного факта: дата подачи сведений и число целевых проверок за период. | Решение пользователя от 2026-10-08: данные не извлекаются из журнала автоматически. |
| D-022 | Правила оценки (формулы, пороги, поля ввода) хранятся в БД в `assessment_criteria` и засеяны миграцией; интерфейс не содержит правил. Пользователь вводит только исходные данные, балл всегда вычисляет система. | Требование архитектуры: методика должна изменяться без правки кода. |
